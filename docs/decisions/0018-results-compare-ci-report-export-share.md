# 0018: Results, compare, baselines, CI report, export and share links

Status: accepted (2026-09-25). Completes SPEC.md §8 (the rest of B2.4) plus B2.5 and B2.6.

## Context
B2.3 ([ADR 0017](0017-server-runner-and-queue.md)) can start a run and persist its attempts, traces and judgments. This task adds the read side (per-attempt results, a full trace, a regression diff between two runs), branch baselines, a CI-ingest endpoint for runs executed by the user's own CI, JSON/HTML export, and public share links.

## Decision

### Diff logic stays in core; the API and CLI both call it
`agentprobe_core.stats.compare_runs(baseline: Mapping[str, CaseSummary], candidate: Mapping[str, CaseSummary], config)` already exists (used by `agentprobe compare`) and needed no changes. `GET /runs/compare` builds each run's `dict[str, CaseSummary]` from its persisted `run_case_summaries` rows and calls the same function. The two shared runs must reference the same `suite_id` (422 otherwise); the `StatisticsConfig` used is the **candidate**'s own suite snapshot, matching the CLI's `_compare`. The result is serialized with `pydantic.TypeAdapter(RegressionReport).dump_python(report, mode="json")`, the same approach the CLI already uses for its own `--json` output — one serialization path for a dataclass tree neither side reimplements.

### `runstore.py` grows read-only helpers that mirror the write-side ones
The existing `load_attempts`/`save_summary`/`save_attempt` take a `Sessions` callable because they run from the queue/worker, which owns its own session lifecycle. Every new **read** endpoint (results, trace, compare, export, share) instead takes the request's own `db: AsyncSession` directly — simpler, and consistent with every other read endpoint in the codebase (`suites.py`, `agents.py`, `projects.py`). New helpers: `read_case_summaries`, `read_attempts`, `read_attempt` (one result), `read_summary` (a `RunSummary` rebuilt via core's `finalize_run`, for JSON/HTML export). The merge of `RunResult.detail` + `Trace.steps` back into an `AttemptResult` is factored into one `_attempt_result()` used by both the background `load_attempts` and the new `read_attempts`.

### `POST /ci/report` requires the suite and agent to already exist
PLAN.md's ADR for `/projects/{id}/runs:ingest` said it "upserts the agent and suite by name." Building an *executable* HTTP agent, or a suite's `test_cases` rows, purely from an ingest payload has real security and data-model cost: the payload is attacker-reachable behind only a project API key, and creating an agent from it would need the same URL/header validation `agents.py` already does, while creating suite rows needs the same versioning rules `suites.py` already does. Since the endpoint's whole point is "persist results the CLI already computed, without the server re-running the suite," and since `finalize_run` needs the *actual* suite (to run the consistency judge and label cases), the suite must already exist in the project — the normal way, via `POST /projects/{id}/suites` — and the agent must already exist via `POST /projects/{id}/agents`. Both are looked up by name, matching `POST /suites/{id}/runs`'s own agent lookup. Missing either is a 422, not an auto-create. Validation (case ids exist, no duplicate `case_id`+`attempt` pairs, the result count fits `runs_per_case`) happens up front, in Python, before any row is written.

**Persistence is one transaction on the request's own session, not the queue's `save_attempt`/`save_summary`.** Those are `Sessions`-based (they open their own session per call) because the queue and worker own their session lifecycle independently of any HTTP request. `/ci/report` is a single request doing one unit of work start to finish — no queue, no SSE, nothing to resume if interrupted — so trying to call them from inside a request handler is actively wrong: in production it would just be a second, redundant connection; in the test harness, where `Db` and the background `Sessions` callable share one connection behind one lock (ADR 0017's `SharedSessions`), it's a **deadlock** (`Depends(get_db)` holds that lock for the whole request, and `save_attempt` tries to take it again). The fix, and the actual design: `runstore.insert_results` / `insert_summary` do the same inserts directly on the caller's `db` session, in one transaction. The per-row field mapping (`AttemptResult` → `run_results` columns, `CaseResult` → `run_case_summaries` columns) is factored into small shared functions (`_attempt_values`, `_case_summary_values`, `_judgment_rows`, `_case_judgment_rows`) that both the live-run path and the ingest path call, so the two can't drift apart even though their insert *mechanics* differ. This was found by a hanging integration test, not by inspection — see Consequences.

- **Size/shape validation:** the payload's `results` field is typed as `list[agentprobe_core.runner.AttemptResult]` directly — core's own frozen, `extra="forbid"` model, so malformed attempts are rejected before any DB work. `results` additionally can't exceed `len(plan_attempts(suite, runs_per_case))`, the same bound a live run enforces, and must be non-empty.
- **Which baseline.** The payload's own `branch` field describes the run being reported (candidate). A separate optional `baseline_branch` says which branch's `Baseline` to diff against; it defaults to `branch` itself, so CI on the trunk branch compares against its own last recorded baseline, while a PR passes `baseline_branch="main"` (or whatever the trunk branch is called) explicitly. If that branch has no recorded baseline, the response's `verdict` is `"no_baseline"` and `comparison` is `null` — never an error, since a repo's first CI report has nothing to compare against.
- Setting the baseline is **not** automatic on ingest. `POST /projects/{id}/baseline` is a separate, deliberate action (e.g. a "record baseline" step run only on merges to the trunk branch), so a bad PR run can never silently become the new baseline.

### `GET /runs/compare`, `GET /runs/{id}/results`, `GET /results/{id}/trace`
- `results` lists **attempts** (one row per `run_results` row, joined to its case key and judgments), matching `GET /results/{id}/trace` taking a `run_results.id`. Filters: `status` (the attempt's), `label` (the case's persisted label), `case` (case key), `attack_category` (the case's `attack_type`). No pagination (out of scope; the existing dashboard-facing endpoints don't paginate either).
- `trace` returns the full reconstructed `AttemptResult` (trace steps included) for one attempt, ownership-checked through `run_results -> runs -> suites -> projects`.

### Export
`GET /runs/{id}/export?format=json|html` recomputes a `RunSummary` via `runstore.read_summary` (core's `finalize_run` over the persisted attempts) rather than trusting the denormalized `run_case_summaries` columns — the strongest guarantee that an export agrees with core's own math. JSON export returns `{run: <RunOut>, summary: <RunSummary>}`; the outer `run.status` carries the true DB status (`queued`/`running`/`failed`/...) since `RunSummary.status` only distinguishes `completed`/`cancelled`.

HTML export (`apps/api/src/agentprobe_api/htmlexport.py`) is one self-contained file: inline `<style>` only, no external stylesheets/fonts/scripts, and **no `<script>` tag at all** — every dynamic value (suite/agent names, case ids, agent output, tool-call arguments, judge reasons) goes through `html.escape()`. Suite and agent names are free-form strings up to 200 characters (not just case ids, which are already pattern-constrained), so they're escaped too, not only the obviously-untrusted agent output. No templating library was added; the report is built with plain string formatting (stdlib only, matches the project's "reach for stdlib first" rule) since one page's worth of tables doesn't need one.

### Share links
`POST /runs/{id}/share` (`expires_in_days: int | None`) mints `secrets.token_urlsafe(32)`, stores only its SHA-256 in `runs.share_token_hash` (already the schema from ADR 0006/0007), and `DELETE` clears both columns. `GET /shared/{token}` is public and reads directly off persisted columns — no `finalize_run` recomputation, so an unauthenticated caller can't trigger the same compute cost the owner's authenticated `export` can. The sanitized view carries: suite/agent **names** (never config or `secret_ref`), run stats/dates, per-case summaries, and per-attempt results with judgment reasons and the agent's `output` text (the point of sharing a run is showing what the agent said). It does **not** include the raw HTTP trace (tool-call argument JSON, per-message role list) or any UUID beyond what's already implied by the token — narrower than the authenticated `/results/{id}/trace`, which stays behind login.

### Amendment (2026-09-26, codebase review)
- The ingest validation moved to core as `agentprobe_core.runner.check_results(suite, runs_per_case, results)` (pure logic belongs in `packages/core`, CLAUDE.md), so the CLI's future `--push` can run the same check before uploading. It is one rule: every result must be a distinct `(case, attempt)` from `plan_attempts`. That rule also closes a gap in the original checks: `attempt` was never range-checked, so a payload could give one case more than `runs_per_case` attempts (skewing its Fisher test) while staying under the total count.
- The HTML export is served with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'` and `X-Content-Type-Options: nosniff`. Escaping stays the defence; the CSP is the backstop, because the export is served on the app's own origin through the `/api` rewrite.

## Consequences
- `/ci/report`'s "auto-create the agent/suite" behavior PLAN.md's ADR originally sketched is **not** built; a project must be set up (suite + agent) before its CI can report into it. Revisit if D2.1/F1 (the CLI's `--push` and the GitHub Action) need a lighter setup flow.
- `GET /runs/{id}/export` and the (authenticated) case/attempt listings are the more complete views; `/shared/{token}` is deliberately smaller. If a future request needs the public view to include the full trace, that's an explicit, reviewable change, not a default.
- Ingesting many results loops `insert_results`' per-attempt inserts (one flush per attempt, to get its id for the trace/judgment rows), not batched. Revisit if CI payloads in practice run past a few thousand attempts.
- Any future request handler that needs to call the queue's `Sessions`-based helpers (`save_attempt`, `save_summary`, `claim`, `load_attempts`, `finish`) synchronously must not also depend on `Db`/`CurrentPrincipal` in the same handler, or must hand the work off via `asyncio.create_task` (as `queue.py`'s `InlineQueue.enqueue` already does) rather than awaiting it inline — otherwise it's the same deadlock in tests.
